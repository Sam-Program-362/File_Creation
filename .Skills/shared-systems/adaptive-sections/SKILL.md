# Adaptive Section Architecture

## Purpose

Choose or create the sections that best represent the actual project. A strange, hybrid, experimental, or highly specific concept must not be distorted merely to fit a conventional template.

**Sections are tools for organizing meaning, not a fixed form that the user must fit.**

## Core rule

Do not use a mandatory universal section template for Analysis Sheets, Character Sheets, World Sheets, or Context Sheets.

A section library may provide useful starting points, but it is not a required checklist.

## Section-building procedure

1. **Identify information units.** Determine what distinct facts, traits, dynamics, mechanisms, events, constraints, and ideas are present.
2. **Identify relationships.** Determine which information belongs together and which information must remain separate to avoid ambiguity.
3. **Determine the document's purpose.** An Analysis Sheet, Character Sheet, World Sheet, Context Sheet, Description, and Lorebook Plan have different audiences and responsibilities.
4. **Select fitting sections.** Use conventional headings only where they represent the information accurately.
5. **Create custom sections.** When no existing heading fits, create a clear project-specific heading. Do not discard or misclassify the information.
6. **Check for misplaced information.** Each section should have a recognizable responsibility.
7. **Remove empty structure.** Do not output empty headings simply because a template contains them.
8. **Validate coverage.** Confirm that important information has a suitable destination in the document and, where appropriate, in related outputs.

## Section responsibility without rigidity

A section should have a coherent purpose. For example:
- Appearance describes physical and visual traits.
- Personality describes behavioral and psychological patterns.
- Backstory describes relevant past events.
- World material describes the setting and its rules.
- Plot material describes story premise, events, and conflicts.
- Scenario material describes a specific opening situation.

These are examples, not a closed taxonomy.

If a character concept requires a section such as `Public Persona and Legal Identity`, `Symbiotic Anatomy`, `Contractual Limitations`, `Memory Partitioning`, or another unusual category, create it.

Do not force cross-cutting information into one unsuitable category. A project-specific section may explain an interaction between character, institution, and world when that relationship is itself important.

## Different output purposes

### Analysis Sheet
May contain:
- information sources and observations;
- established, supported, inferred, proposed, and unknown details;
- concept interpretation;
- relevant tags and Bedrock candidates;
- development choices and generation direction.

These are possible analysis modules, not mandatory headings.

### Character Sheet
Contains the completed information needed to understand the character. Select or create sections around that character's actual identity, traits, roles, behavior, abilities, limitations, history, relationships, and other relevant details.

### World Sheet
Contains the setting information needed for this concept. Select or create sections around its actual geography, systems, institutions, cultures, rules, histories, locations, and unusual structures.

### Context Sheet
Contains a complete, integrated, downstream-facing account of the project. It must organize every relevant aspect the narrator/roleplayer AI needs. It must not use analysis-only headings such as `Provided Elements`, `Missing Elements`, or `Planned Expansion`.

### Description
Uses a human-facing structure appropriate to the concept's presentation. It is not a Context Sheet with fewer headings.

### Lorebook Plan
Uses a structure that explains the implementation handoff. The plan may have lorebook-level sections and entry-level briefs, but it is not constrained to a single fixed number or category of entries.

## Avoid these failures

- Do not force every character into the same five sections.
- Do not force every world into geography/history/culture/factions if those do not fit.
- Do not create `World Context` for a project with no meaningful world component merely to fill a template.
- Do not discard unusual details because they seem difficult to classify.
- Do not hide important information in an unrelated section for convenience.
- Do not merge separate ideas so aggressively that their individual meanings disappear.
- Do not make every detail its own heading; group related information when that improves usability.

## Refinement

When refining a section:
- Preserve the section's responsibility.
- Add or rename sections when the project has evolved beyond the current structure.
- Move information only when the requested change requires it.
- Preserve unrelated wording and unaffected sections.
- If a detail is relevant to multiple documents, use the Information Transfer skill rather than solving the issue by stuffing it into an oversized section.

## Completion check

- [ ] Sections reflect the actual project.
- [ ] Custom sections were created when needed.
- [ ] No important information was omitted for lack of a suitable heading.
- [ ] No empty template sections remain.
- [ ] Sections have clear responsibilities.
- [ ] The structure serves the document's actual audience and purpose.
